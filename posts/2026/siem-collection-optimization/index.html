안정화 및 성능 개선

01

Overview

빠르게 요청하는 것보다 안정적으로 끝내는 것이 중요했습니다.

월간보고서에 필요한 데이터는 FortiSIEM과 PRTG에서 서로 다른 방식으로 수집되고 있었습니다. FortiSIEM 데이터는 매일 새벽 02시에 미리 수집하고, PRTG 데이터는 사용자가 월간보고서 PDF 생성을 요청하는 시점에 실시간으로 조회했습니다.

문제는 두 외부 시스템 모두 이미 높은 부하를 받고 있는 상황에서, 기존 애플리케이션이 응답 특성과 처리 용량을 충분히 고려하지 않고 요청하고 있었다는 점입니다. 그 결과 일부 데이터가 누락되고, 재시도가 오히려 외부 시스템의 부하를 키우는 문제가 반복됐습니다.

약 220GB / day IDC 이관 중 FortiSIEM의
매일 처리하던 로그 데이터 양
SIEM 부하 60% FortiSIEM 지속적인 평균 부하
PRTG 부하 40% PRTG 기존 평균 부하
40분 → 15분 PRTG 개선 후 월간보고서 평균 생성 시간을 63% 감소

PRTG 데이터는 PDF 생성 응답시간과 직접 연결되므로 안정성과 처리시간을 함께 개선해야 했습니다.

03

Problem

문제는 네트워크가 아니라 수집 방식 자체에 있었습니다.

FortiSIEM

수집은 완료되지만 데이터가 맞지 않았습니다.

  • 국가 코드와 조회 쿼리 조건의 정합성 문제
  • 높은 시스템 부하를 고려하지 않은 짧은 요청 간격
  • 3회 재시도 소진 후 일부 데이터 누락 가능성
  • 수집 상태를 확인할 별도 모니터링 없이 .txt 로그에 의존
PRTG

빠른 비동기 요청이 오히려 전체 처리를 느리게 했습니다.

  • 일부 방화벽 인터페이스 설정 누락
  • 인터페이스별 800~2,000개 이상의 월간 데이터 응답
  • 응답 지연을 실패처럼 취급하며 무분별한 재시도 발생
  • HTTP 429와 자원 부하 알람이 반복적으로 발생
“응답이 느리다”와 “요청이 실패했다”를 동일한 문제로 취급하면, 재시도가 오히려 성능 저하를 유발하고, 장애를 증폭시킬 수 있었습니다.
04

FortiSIEM

속도를 늦추고 데이터 정합성과 완료 가능성을 높였습니다.

01

조회 쿼리와 국가 코드 정합성 수정

실제 보고서 데이터와 수집 결과가 일치하지 않는 지점을 추적해 국가 코드 처리와 FortiSIEM 조회 조건을 수정했습니다.
재시도 정책을 바꾸기 전에 잘못된 조회 자체가 발생하지 않도록 정리했습니다.

02

요청 간격 확대

FortiSIEM이 IDC 이관으로 높은 부하를 지속적으로 받고 있다는 점을 고려해 요청 사이의 간격을 늘렸습니다.
처리량을 최대화하기보다 외부 시스템이 안정적으로 응답할 수 있는 수준으로 요청 속도를 낮췄습니다.

03

재시도 3회 → 5회

일시적인 응답 지연으로 수집 작업 전체가 실패하지 않도록 재시도 횟수를 늘렸습니다.
단순히 횟수만 늘리는 대신 요청 간격도 함께 조정해 추가 부하를 최소화했습니다.

Before 평균 약 2시간

더 빠르지만 일부 데이터 누락 가능성이 존재

→
After 평균 3시간 30분+

업무 시간 이전 완료 + 데이터 정합성 및 안정성 확보

💡새벽 02시에 시작하는 배치 특성상 데이터 수집 실행 시간의 증가로 인해 업무에 영향을 주지 않았기 때문에, 처리속도보다 데이터 정합성과 외부 시스템 안정성을 우선했습니다.

05

PRTG

무분별한 병렬 처리 대신 제한된 동시성을 선택했습니다.

PRTG 문제를 조사하면서 먼저 일부 인터페이스 설정이 누락되어 필요한 데이터 자체가 조회되지 않는 상태를 확인하고 설정을 정비했습니다. 이후 요청별 소요 시간을 로그로 남겨 실제 응답 특성을 확인했습니다.

인터페이스에 따라 응답에 수 초에서 수십 초가 걸렸고, 기존 로직은 이 대기 시간을 충분히 고려하지 않은 채 새로운 요청과 재시도를 계속 발생시키고 있었습니다. 결과적으로 비동기 처리의 병렬성이 PRTG가 감당할 수 있는 수준을 넘어가면서 HTTP 429와 자원 부하 알람으로 이어졌습니다.

Before
  1. 다수 인터페이스에 동시에 요청
  2. 응답 지연
  3. 추가 재시도
  4. PRTG 부하 증가
  5. 429 / 응답 실패
  6. 다시 재시도
→
After
  1. 동시 요청 최대 3개로 제한
  2. 응답 완료 후 다음 작업 처리
  3. Exponential Backoff 적용
  4. Jitter로 재시도 시점 분산
  5. 불필요한 요청 감소
  6. 안정적인 데이터 수집
Bounded Concurrency

비동기 처리를 제거한 것이 아니라, 동시에 처리할 인터페이스를 최대 3개로 제한했습니다.
병렬성은 유지하면서 외부 시스템이 감당할 수 있는 범위 안에서 처리량을 제어했습니다.

06

Result

불필요한 요청을 없애고 안정성과 처리시간을 개선했습니다.

FortiSIEM 데이터 정합성 개선

조회 쿼리와 국가 코드 수정으로 잘못된 조건에 의한 데이터 누락을 개선했습니다.

PRTG 부하 알람 해소

과도한 요청과 재시도를 줄여 월간보고서 생성 시 발생하던 자원 부하 알람을 제거했습니다.

Report 약 62.5% 단축

월간보고서 평균 생성 시간을 약 40분에서 15분으로 단축했습니다.

What I learned

외부 시스템 연동에서 “더 많은 병렬 요청”이 항상 더 높은 성능을 의미하지는 않습니다.

시스템의 응답 특성과 처리 용량을 확인하지 않은 비동기 처리와 재시도는 장애를 스스로 증폭시킬 수 있습니다.
이번 개선에서는 요청별 응답 시간을 직접 계측하고, 시스템별 업무 특성을 기준으로 서로 다른 전략을 적용했습니다.

  • FortiSIEM: 처리속도보다 정합성과 안정성을 우선
  • PRTG: 동시성 제한과 재시도 정책 개선으로 안정성과 성능을 동시에 확보
  • 운영 문제를 단순 네트워크 장애로 결론내리지 않고 데이터와 로그로 원인을 검증
