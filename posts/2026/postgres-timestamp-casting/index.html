01

Overview

새로 설계하는 것보다 기존 구조를 이해하고 안전하게 변경하는 것이 더 어려웠습니다.

기존 그룹웨어 서비스의 운영 데이터를 MySQL에서 PostgreSQL로 이전해야 했습니다. 일반적인 데이터베이스 마이그레이션과 달리, 이관 대상 PostgreSQL에는 이미 애플리케이션 구현이 완료된 테이블이 존재했고 실제 기능 역시 해당 스키마를 기준으로 동작하고 있었습니다.

하지만 데이터베이스를 분석하면서 기본 키가 존재하지 않는 테이블, 올바르지 않은 외래 키, 불완전한 제약조건과 연관관계 등 여러 구조적 문제를 확인했습니다. 이미 구현된 SQLAlchemy 모델과 서비스 코드가 기존 구조에 의존하고 있어 스키마 자체를 대규모로 수정하는 것도 위험한 상황이었습니다.

동시에 인증 영역에서는 Access Token만 발급하는 구조로 인해 토큰이 만료될 때마다 로그인이 종료되고, 클라이언트에서 토큰이 그대로 노출되는 문제도 존재했습니다. 따라서 데이터 마이그레이션과 함께 기존 인증 구조도 개선했습니다.

26 Tables 직접 관계와 데이터 의존성을 분석한 레거시 테이블
2 Weeks+ 테이블 분석 및 데이터 이관 계획 수립에 소요된 기간
30 min 기존 Access Token 만료로 로그인이 종료되던 주기
10 min 개선 후 Access Token 유효시간
02

Constraints

문제를 발견했다고 해서 스키마를 자유롭게 수정할 수 있는 환경은 아니었습니다.

Database

데이터베이스 구조와 실제 데이터 관계가 일치하지 않았습니다.

  • 일부 테이블에 명확한 Primary Key가 존재하지 않음
  • Foreign Key와 실제 데이터 참조 관계가 일치하지 않음
  • 제약조건만으로 테이블 관계를 신뢰하기 어려운 상태
  • 26개 테이블의 데이터 의존관계를 별도로 파악해야 함
Application

이미 구현된 애플리케이션이 기존 스키마에 강하게 의존하고 있었습니다.

  • SQLAlchemy가 기존 PostgreSQL 스키마 기준으로 구현됨
  • 스키마 변경 시 기존 서비스 코드까지 영향 받을 가능성 존재
  • Alembic migration history가 정상적으로 관리가 안된 상태
  • 대규모 스키마 수정은 일정과 안정성 측면에서 위험도 높음
데이터베이스를 이상적인 형태로 다시 설계하는 것보다, 현재 동작하는 시스템을 깨뜨리지 않으면서 데이터를 정확하게 옮기는 것을 우선했습니다.
03

Schema Analysis

제약조건이 아니라 실제 데이터를 기준으로 26개 테이블의 관계를 다시 추적했습니다.

PK·FK 정보만으로는 테이블의 실제 연관관계를 판단하기 어려웠기 때문에 각 테이블을 직접 SELECT하여 데이터 형태와 참조 값을 확인했습니다. 이후 관련 테이블을 JOIN하면서 어떤 컬럼이 실제 식별자 역할을 하고, 어떤 순서로 데이터가 연결되는지 역으로 분석했습니다.

특히 단순히 전체 데이터를 INSERT하는 방식은 사용하지 않았습니다. 부모 데이터와 자식 데이터의 연결이 올바른지, 기존 MySQL의 데이터 관계가 PostgreSQL에서도 동일하게 유지되는지를 확인하면서 테이블별 이관 방법을 결정했습니다.

01

테이블 구조 및 데이터 조사

26개 테이블의 컬럼, PK·FK, NULL 허용 여부와 제약조건을 확인하고 실제 저장된 데이터를 조회하여 스키마 정의와 데이터 관계가 일치하는지 비교했습니다.

02

SELECT · JOIN 기반 관계 검증

제약조건을 신뢰하기 어려운 테이블은 실제 식별 값을 기준으로 JOIN하여 데이터 간 연결 관계를 확인하고, 누락되거나 잘못 연결된 데이터를 이관 전에 식별했습니다.

03

데이터 의존관계 및 이관 순서 수립

참조 대상이 되는 데이터가 먼저 존재해야 하는 관계를 기준으로 테이블 간 의존성을 정리하고, 데이터 삽입 순서를 수립했습니다.

04

Migration Strategy

마이그레이션의 기준을 “INSERT 성공”이 아니라 “관계가 유지되는가”로 잡았습니다.

Risk
  1. MySQL 원본 데이터 조회
  2. 단순 테이블 단위 INSERT
  3. 잘못된 참조 관계까지 그대로 이관
  4. 애플리케이션 실행 시점에 문제 발견
→
Applied
  1. MySQL 원본 데이터 분석
  2. SELECT · JOIN으로 관계 사전 검증
  3. 의존관계에 따라 순차적으로 데이터 이관
  4. PostgreSQL에서 다시 JOIN하여 결과 검증
Validation First

마이그레이션 쿼리가 정상 종료됐다는 사실만으로 성공을 판단하지 않았습니다. 이관 전후의 레코드와 참조 관계를 비교하고, PostgreSQL에서도 동일한 JOIN 결과가 만들어지는지를 확인하여 데이터 정합성을 검증했습니다.

Option A 기존 스키마 재설계

구조적으로는 이상적이지만 기존 SQLAlchemy 모델과 서비스 로직, 운영 일정에 미치는 영향이 큼

→
Selected 기존 구조 유지 + 데이터 검증

변경 범위를 제한하고 실제 데이터 관계를 분석하여 운영 안정성을 유지하면서 마이그레이션 수행

05

Authentication Problem

기존 JWT는 인증 토큰을 발급했지만 로그인 상태를 유지하지 못했습니다.

기존 인증 구조에서는 로그인 시 Access Token 하나만 발급했습니다. Access Token의 유효시간은 약 30분이었고, 토큰이 만료되면 사용자는 다시 로그인해야 했습니다.

또한 클라이언트에서 인증 토큰이 직접 노출되는 구조였으며, 서버에서 토큰의 수명 주기나 재사용을 제어할 수 있는 별도의 Refresh Token 관리 구조도 존재하지 않았습니다.

Session

Access Token 만료가 곧 로그인 종료였습니다.

  • Access Token만 발급
  • 약 30분 후 인증 만료
  • 자동 재발급 구조 없음
  • 사용자가 반복적으로 다시 로그인해야 함
Security

토큰의 발급 이후 수명 주기를 관리하기 어려웠습니다.

  • Refresh Token 관리 구조 부재
  • 토큰 재사용을 제어할 Rotation 정책 부재
  • 로그아웃된 토큰을 별도로 무효화할 수단 부족
  • Access Token Payload에 불필요한 정보 포함
06

JWT Redesign

Access Token과 Refresh Token의 역할을 분리하고 토큰 수명 주기를 관리했습니다.

01

Refresh Token 기반 재발급 구조 구현

Access Token이 만료되더라도 유효한 Refresh Token을 통해 새로운 Access Token을 발급받을 수 있도록 변경하여 로그인 상태를 유지할 수 있도록 했습니다.

02

Access Token 유효시간 및 Payload 최소화

Access Token 유효시간을 기존 30분에서 10분으로 줄이고, Payload에는 회원 식별을 위한 ID와 권한 정보인 Role만 포함하도록 불필요한 정보를 제거했습니다.

03

Refresh Token Rotation

Refresh Token을 사용할 때 새로운 토큰을 발급하고 기존 토큰을 더 이상 사용할 수 없도록 처리하여, 동일한 Refresh Token이 지속적으로 재사용되는 것을 방지했습니다.

04

토큰 해시 저장 및 Blacklist

Refresh Token 원문을 그대로 저장하지 않고 해시 값을 저장하여 서버 저장소가 노출될 경우의 위험을 줄이고, 폐기된 토큰을 Blacklist로 관리하여 재사용을 제한했습니다.

05

Secure Cookie 적용

Refresh Token을 Secure Cookie를 통해 전달하도록 변경하여 기존 인증 방식에서 발생하던 클라이언트 측 토큰 노출 위험을 줄였습니다.

06

프론트엔드 사용자 상태 관리

React 프론트엔드에서는 Zustand를 이용해 인증된 사용자 정보를 전역 상태로 관리하도록 변경하여 로그인 상태와 사용자 정보를 여러 화면에서 일관되게 사용할 수 있도록 개선했습니다.

Before
  1. 로그인
  2. Access Token 단독 발급
  3. 약 30분 후 토큰 만료
  4. 인증 상태 종료
  5. 사용자 재로그인
→
After
  1. Access + Refresh Token 발급
  2. Access Token 10분 사용
  3. Refresh Token으로 재발급
  4. Rotation으로 기존 Refresh Token 폐기
  5. 인증 상태 유지
Token Lifecycle

단순히 Refresh Token을 추가하는 것에 그치지 않고, 발급 → 저장 → 검증 → 재발급 → Rotation → 폐기까지 토큰의 전체 수명 주기를 서버에서 관리할 수 있도록 구조를 변경했습니다.

07

Result

기존 시스템의 변경 범위를 최소화하면서 데이터와 인증 구조의 신뢰성을 높였습니다.

Database 26개 테이블 관계 분석

불완전한 PK·FK와 제약조건에 의존하지 않고 실제 데이터를 기준으로 테이블 관계와 이관 순서를 정리했습니다.

Migration 데이터 정합성 확보

SELECT·JOIN 기반의 사전·사후 검증을 통해 데이터 누락과 잘못된 참조 관계를 확인하며 운영 데이터를 이관했습니다.

Authentication 로그인 유지 구조 구현

Refresh Token과 Rotation, Blacklist, 해시 저장을 적용해 토큰의 발급부터 폐기까지 관리 가능한 인증 구조로 개선했습니다.

What I learned

레거시 시스템에서는 가장 이상적인 구조보다 현재 시스템을 안전하게 개선할 수 있는 방법을 찾는 것이 중요했습니다.

데이터베이스의 구조적 문제를 발견했지만 이미 구현된 애플리케이션과 운영 환경에 미치는 영향을 고려해 대규모 스키마 변경 대신 실제 데이터 관계를 분석하고 검증하는 방법을 선택했습니다. 인증 역시 기능 추가에 그치지 않고 토큰의 저장과 재발급, 재사용 방지와 폐기까지 하나의 수명 주기로 바라보고 개선했습니다.

  • 스키마 정의만 신뢰하지 않고 실제 데이터를 통해 테이블 관계를 검증
  • 변경에 따른 영향 범위를 고려하여 마이그레이션 전략을 결정
  • 데이터 이관 성공 여부를 INSERT 결과가 아닌 참조 관계와 정합성으로 판단
  • JWT를 단순 토큰 발급 기능이 아닌 수명 주기를 가진 인증 구조로 개선
