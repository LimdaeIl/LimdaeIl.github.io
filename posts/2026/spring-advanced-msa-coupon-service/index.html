Team Project

Spring Cloud 기반 MSA 환경에서 회원·쿠폰 도메인을 담당했습니다.

교육 후반에는 Backend 4명이 팀을 구성해 MSA 기반 서비스를 구현했습니다. 이 과정에서 회원과 쿠폰 도메인을 담당하고, 인증·인가부터 쿠폰 발급 동시성 제어까지 핵심 백엔드 기능을 구현했습니다.

단순히 서비스를 여러 개로 나누는 데 그치지 않고 Gateway, Service Discovery, 공통 응답 규격, 모니터링 등 분산된 서비스가 하나의 시스템으로 동작하기 위해 필요한 기반도 함께 구성했습니다.

04

Concurrency

쿠폰 발급 경쟁을 Redis 분산 락으로 제어했습니다.

한정된 수량의 쿠폰에 다수 사용자가 동시에 접근하면 여러 애플리케이션 인스턴스에서 같은 쿠폰 수량을 동시에 변경할 수 있습니다. 단일 JVM의 synchronized만으로는 MSA·다중 인스턴스 환경의 동시성을 보장할 수 없기 때문에 Redis 기반 분산 락을 적용했습니다.

Redisson을 이용해 쿠폰 발급 임계 영역에 대한 락을 획득한 뒤 발급 가능 여부 확인과 수량 변경을 수행하도록 구성하여, 동시에 요청이 유입되더라도 쿠폰 수량을 기준으로 일관된 발급 흐름을 유지하도록 설계했습니다.

Problem
  1. 동일 쿠폰에 동시 발급 요청
  2. 여러 인스턴스에서 동일 데이터 접근
  3. 발급 가능 여부 동시 검증
  4. 쿠폰 수량 정합성 위험
→
Applied
  1. Redis / Redisson Lock
  2. 분산 환경 공통 Lock 획득
  3. 발급 임계 영역 직렬화
  4. 쿠폰 발급 동시성 제어
동시성 제어의 범위가 단일 프로세스를 넘어가는 순간, 애플리케이션 인스턴스들이 공유할 수 있는 동기화 수단이 필요했습니다.
05

Async Processing

Kafka 기반 비동기 처리로 대량 쿠폰 발급 요청을 분리했습니다.

쿠폰 발급 요청을 동기적으로 모두 처리하면 요청량이 증가할수록 API 서버의 처리 부하도 함께 증가합니다. 이를 완화하기 위해 Kafka 기반 비동기 처리 구조를 적용해 요청 수신과 실제 발급 처리를 분리했습니다.

메시지 큐를 통해 요청을 전달함으로써 대량 요청을 즉시 처리해야 하는 부담을 줄이고, Consumer가 메시지를 처리하는 구조를 경험했습니다. 이 과정에서 메시지 기반 시스템이 단순한 비동기 호출이 아니라 서비스 간 결합도와 트래픽 처리 방식 자체를 바꾸는 아키텍처라는 점을 학습했습니다.

Synchronous Request → Issue → Response

요청 처리와 쿠폰 발급 작업이 직접 결합되어 대량 요청이 API 처리 부하로 이어집니다.

→
Asynchronous Request → Kafka → Consumer

요청 수신과 발급 처리를 분리해 메시지 큐를 통한 비동기 처리와 부하 분산 구조를 적용했습니다.

06

Load Test

JMeter 10만 건 부하 테스트로 대량 요청 환경의 쿠폰 발급 구조를 검증했습니다.

구현이 완료된 뒤에는 정상적인 단일 요청만 확인하는 데 그치지 않고 JMeter를 활용해 총 10만 건 규모의 부하 테스트를 수행했습니다. 이를 통해 대량 요청 상황에서도 쿠폰 발급 구조가 안정적으로 동작하는지 검증했습니다.

이 경험을 통해 동시성 제어는 Lock을 적용하는 것으로 끝나는 것이 아니라, 실제 부하 상황을 만들어 데이터 정합성과 시스템 동작을 함께 확인해야 한다는 점을 배웠습니다.

Redis 분산 락 기반 동시성 제어

07

MSA Standard

서비스가 분리될수록 공통 통신 규격이 중요했습니다.

MSA에서는 각 서비스가 독립적으로 개발되기 때문에 API 응답과 오류 표현 방식이 제각각이면 서비스 간 통신과 클라이언트 처리가 복잡해집니다. 팀에서는 공통 DTO와 에러 응답 포맷, API 버전 관리 규칙을 정의했습니다.

이를 통해 개별 서비스의 내부 구현은 분리하면서도 외부에 노출되는 인터페이스에는 일관된 규칙을 적용하고, 서비스 간 협업과 유지보수성을 높이는 방향을 경험했습니다.

01

Common DTO

서비스 간 전달되는 데이터 구조의 공통 규칙을 정의했습니다.

02

Error Response

에러 코드와 응답 포맷을 통일해 서비스별 오류 표현 차이를 줄였습니다.

03

API Versioning

API 버전 관리 규칙을 정의해 변경에 따른 서비스 간 영향을 관리했습니다.

08

Monitoring

구현 이후의 상태를 확인할 수 있도록 모니터링과 알림 환경을 구성했습니다.

분산된 서비스는 특정 인스턴스의 장애나 자원 이상을 애플리케이션 로그만으로 빠르게 파악하기 어렵습니다. Prometheus로 메트릭을 수집하고 Grafana를 통해 시각화하는 기본 모니터링 환경을 구성했습니다.

여기에 Slack 알림을 연계해 서비스 상태와 장애 징후를 확인할 수 있도록 구성하면서, 백엔드 개발의 범위를 기능 구현에서 끝내지 않고 배포 이후 서비스 상태를 관찰하는 운영 관점까지 확장했습니다.

What I learned

MSA는 서비스를 나누는 기술이 아니라 분산된 시스템의 복잡성을 관리하는 설계라는 점을 배웠습니다.

Spring Cloud, Redis, Kafka, Prometheus 같은 기술을 개별적으로 사용하는 것보다 어떤 문제를 해결하기 위해 도입하는지 이해하는 것이 중요했습니다. 특히 쿠폰 발급 기능을 구현하며 동시성, 비동기 처리, 부하 테스트를 하나의 흐름으로 경험했고, 서비스가 분산될수록 통신 규격과 관측 가능성 역시 중요한 설계 요소가 된다는 점을 확인했습니다.

  • Redis(Redisson) 분산 락 기반 쿠폰 발급 동시성 제어
  • Kafka 기반 비동기 처리와 대량 요청 부하 분산 구조 경험
