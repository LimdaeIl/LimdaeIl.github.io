모임 참가 정원 동시성 제어와
비관적 락 설계

모임 최대 참가자 수가 12명인 상황에서 여러 사용자가 동시에 참가 요청을 보내면 동일한 참석자 수를 기준으로 검증을 통과해 초과 참석이 발생할 수 있었습니다. 정원 체크와 참석 처리를 하나의 임계 구간으로 보고, groupId 단위로 Group Row를 비관적 락으로 직렬화하여 정합성을 보장했습니다.

카테고리 : Backend / Concurrency / Transaction · 2025.11 ~ 2026.01
Java Spring Boot JPA MySQL
01

Overview

정원이 12명인데 동시에 요청이 들어오면 13명이 참석할 수 있었습니다.

FREE 정책의 모임은 사용자가 참가 버튼을 누르는 순간 바로 ATTEND 상태로 변경됩니다. 이때 여러 요청이 동시에 들어오면 각 트랜잭션이 같은 참석자 수를 조회한 뒤 모두 정원 검증을 통과할 수 있습니다.

예를 들어 현재 참석자가 11명이고 정원이 12명인 모임에 요청 A와 B가 거의 동시에 들어오면 두 요청 모두 count=11을 읽고 통과한 뒤, 각각 참석 처리를 수행하여 최종 참석자가 13명이 되는 overbooking이 발생할 수 있습니다.

현재 인원: 11 동시 요청 직전 현재 참석자 수
최대 인원: 12 모임의 최대 참가 정원
요청 인원: 2 동시에 들어온 참가 요청
최종 인원: 13 동시성 제어가 없을 때 발생 가능한 최종 참석자 수
02

Race Condition

정원 체크와 참석 처리가 하나의 임계 구간인데 서로 다른 트랜잭션에서 동시에 실행됐습니다.

문제의 핵심은 단순한 count 조회가 아니라 검증(check)과 변경(write)이 분리된 상태로 동시에 실행된다는 점이었습니다. 정원 체크에서 읽은 값이 참석 처리 전에 이미 다른 트랜잭션에 의해 바뀔 수 있기 때문에, 단순 if문으로는 정합성을 보장할 수 없었습니다.

Parallel
  1. A가 count = 11 조회
  2. B도 count = 11 조회
  3. A 정원 검증 통과
  4. B 정원 검증 통과
  5. A 참석 → 12명
  6. B 참석 → 13명
→
Required
  1. A가 정원 체크 + 참석 처리
  2. A Commit
  3. B가 최신 상태에서 다시 count 조회
  4. B는 count = 12 확인
  5. 정원 초과로 실패
같은 groupId에 대한 “정원 체크 + 참석 처리”는
결과적으로 한 번에 하나의 트랜잭션만 실행되어야 했습니다.
03

Lock Decision

충돌이 정원 막바지에 집중될 수 있어 비관적 락으로 임계 구간을 직렬화했습니다.

synchronized는 단일 JVM 내부에서는 동작하지만 서버 인스턴스가 늘어나면 프로세스 간 정합성을 보장하지 못합니다. 정원 제한은 애플리케이션 메모리의 규칙이 아니라 데이터 자체의 정합성 규칙이므로 DB 트랜잭션 수준에서 보장해야 한다고 판단했습니다.

낙관적 락도 대안이지만 정원 막바지에서는 동일 모임에 여러 요청이 몰릴 가능성이 높아 충돌 감지 이후의 Retry 정책이 복잡해질 수 있습니다. 따라서 충돌을 사전에 막고 후행 요청을 대기시키는 비관적 락을 선택했습니다.

Optimistic Lock 충돌 후 감지

충돌이 적을 때 효율적이지만, 정원 막바지처럼 충돌이 반복되면 Retry 횟수와 응답시간, 상태 변경을 함께 관리해야 하는 부담이 커질 수 있습니다.

→
Selected Pessimistic Lock

임계 구간에 진입하기 전에 DB Row를 먼저 잠그고 동일 모임 요청을 순차 처리하여 정원 정합성을 우선했습니다.

04

Lock Granularity

참석자 테이블이 아니라 Group Row를 잠가 groupId 단위로 경쟁 범위를 제한했습니다.

정원 체크는 참석 테이블에서 ATTEND 상태의 Row 개수를 세어 판단합니다. 하지만 동시성 제어의 기준은 참석 Row가 아니라 모임 자체였습니다. 같은 모임의 참가 요청끼리는 경쟁해야 하지만 서로 다른 모임은 독립적으로 처리되어야 하기 때문입니다.

참석 테이블에만 락을 걸 경우 아직 생성되지 않은 신규 참석 Row는 잠글 대상이 없고, count + insert 조합 전체를 하나의 Row Lock으로 보호하기 어렵습니다. 반면 Group Row는 항상 하나 존재하므로 해당 Row를 임계 구간의 Gate로 사용할 수 있었습니다.

GroupUser Lock

count 대상 Row만 잠그는 방식에는 빈틈이 있었습니다.

  • count는 여러 Row를 읽음
  • 아직 생성되지 않은 참가 Row는 잠글 수 없음
  • 새로운 INSERT까지 직렬화하기 어려움
Group Lock

Group Row를 모임 단위 동시성의 진입점으로 사용했습니다.

  • 모임마다 항상 하나의 Row 존재
  • 같은 groupId 요청만 서로 대기
  • 다른 모임 요청은 서로 영향 없음
Lock Granularity

락 대상은 “어떤 테이블을 조회하는가”가 아니라 “어떤 비즈니스 단위의 요청을 직렬화해야 하는가”를 기준으로 결정했습니다.

05

Transaction Flow

반드시 락을 먼저 획득한 뒤 참석자 수를 조회하도록 순서를 고정했습니다.

JPA의 PESSIMISTIC_WRITE를 사용해 Group Row를 조회하면 DB에서는 SELECT ... FOR UPDATE에 해당하는 쓰기 잠금이 획득됩니다. 같은 Group Row를 잠그려는 후행 트랜잭션은 선행 트랜잭션이 Commit 또는 Rollback할 때까지 대기합니다.

중요한 점은 count 쿼리를 실행하기 전에 이미 Group Row Lock을 획득한다는 것입니다. 따라서 같은 모임에 대한 다른 attend·approve·left 흐름은 임계 구간에 들어올 수 없고, 현재 트랜잭션은 최신 참석 상태를 기준으로 정원 검증을 수행할 수 있습니다.

Request A
  1. Transaction 시작
  2. Group FOR UPDATE
  3. 참석자 count 조회
  4. 정원 검증
  5. ATTEND 처리
  6. 필요 시 FULL 전환
  7. Commit 및 Lock 해제
→
Request B
  1. 동일 Group Lock 요청
  2. A 처리 중 DB에서 대기
  3. A Commit 후 Lock 획득
  4. 변경된 최신 count 조회
  5. 정원 초과 여부 재검증
count 쿼리 자체를 잠그는 것이 아니라 count의 기준이 되는 “모임의 상태 변경 흐름”을 먼저 잠갔습니다.
06

Participation Policy

FREE와 APPROVAL_REQUIRED의 차이는 락 여부가 아니라 정원 체크 시점이었습니다.

FREE 모임에서는 참가 요청과 동시에 ATTEND 상태가 되므로 attend()에서 정원 검증이 발생합니다. 반면 APPROVAL_REQUIRED 정책에서는 신청 시점에는 PENDING 상태이고, 실제 참석 인원이 증가하는 approve() 시점에 정원을 확인해야 합니다.

FREE attend()에서 Lock

참가 요청 자체가 참석 인원을 증가시키므로 정원 체크와 ATTEND 처리를 동일 트랜잭션 안에서 직렬화했습니다.

↔
APPROVAL_REQUIRED approve()에서 Lock

신청 단계는 PENDING이므로 정원과 직접 연관되지 않고, 승인 순간 실제 참석 인원이 증가하기 때문에 approve()에서 락을 획득했습니다.

01

attend()

FREE 정책에서 참석 인원이 증가하는 진입점이므로 Group Row Lock 이후 정원 체크와 참석 처리를 수행했습니다.

02

approve()

APPROVAL_REQUIRED 정책에서 PENDING 사용자가 실제 ATTEND로 전환되는 시점이므로 같은 정원 검증 규칙을 적용했습니다.

03

left() · kick() · ban()

참석 인원이 감소하거나 모임 상태가 FULL ↔ RECRUITING으로 바뀔 수 있는 흐름도 동일한 groupId 단위 직렬화 규칙 안에서 처리했습니다.

07

Trade-off

정합성을 얻는 대신 같은 모임에 대한 요청은 Lock Wait 비용을 감수했습니다.

Waiting

같은 모임의 동시 요청은 선행 트랜잭션이 끝날 때까지 대기합니다.

  • 동일 groupId 요청은 순차 처리
  • 동시 요청이 많을수록 대기시간 증가
  • 락 점유 구간을 짧게 유지할 필요
Deadlock

현재 구조에서는 단일 Group Row만 잠가 락 순서를 단순하게 유지했습니다.

  • 하나의 groupId에 대해 하나의 Row Lock
  • 중첩된 다중 Row Lock 구조가 아님
  • 순환 대기 가능성을 낮춘 단순한 락 범위
Consistency First

한 모임에 동시에 수십·수백 요청이 몰리는 상황은 일반적이지 않고, 정원 막바지에서는 응답속도보다 정원 규칙의 정합성이 더 중요하다고 판단했습니다.

08

Result

정원 제한을 개별 API의 if문이 아니라 groupId 단위의 트랜잭션 규칙으로 설계했습니다.

Race Condition Overbooking 방지

동일 count를 여러 요청이 동시에 읽는 구조를 제거하고 최신 참석 상태를 기준으로 정원 검증이 수행되도록 했습니다.

Lock Scope groupId 단위 직렬화

동일 모임 요청만 서로 대기하고 서로 다른 모임은 독립적으로 처리될 수 있도록 락 범위를 설계했습니다.

Domain Rule 참석 변경 흐름 통일

attend·approve·left·kick·ban 등 참석 인원에 영향을 주는 모든 흐름에 동일한 동시성 규칙을 적용했습니다.

What I learned

동시성 제어의 핵심은 count 쿼리를 잠그는 것이 아니라 비즈니스 경쟁 단위를 정확히 찾는 것이었습니다.

처음에는 참석자 테이블에서 count만 정확히 확인하면 된다고 생각했지만, 문제는 count와 이후 상태 변경 사이의 임계 구간 전체에 있었습니다. 같은 모임의 참석 관련 트랜잭션을 Group Row 하나를 기준으로 직렬화하면서, 락 대상은 조회 테이블이 아니라 비즈니스 규칙의 경쟁 단위로 결정해야 한다는 점을 배웠습니다.

  • 정원 체크 + 참석 처리는 하나의 임계 구간으로 다뤄야 함
  • 정원 제한은 애플리케이션 메모리가 아니라 DB 트랜잭션 수준에서 보장
  • count 대상 테이블보다 groupId라는 경쟁 단위를 기준으로 Lock Granularity 결정
  • FREE·APPROVAL_REQUIRED 정책별로 실제 참석 인원이 변하는 시점에 Lock 적용
  • 참석 증가·감소와 FULL ↔ RECRUITING 상태 전환까지 동일한 직렬화 규칙으로 통일
