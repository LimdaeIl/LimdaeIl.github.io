01

Overview

데이터가 적을 때의 빠른 응답은 쿼리가 효율적이라는 증거가 아니었습니다.

개발 초기에는 데이터가 많지 않아 대부분의 조회 API가 빠르게 응답했습니다. 그러나 이 환경에서는 인덱스를 사용하지 않거나 불필요한 정렬이 발생해도 체감 성능 차이가 작아 병목을 발견하기 어려웠습니다.

실제 데이터 증가 상황을 가정하기 위해 약 10만 건 규모의 테스트 데이터를 구성하고, 조건 검색과 정렬이 함께 사용되는 조회 API를 중심으로 실행 계획을 확인했습니다. 단순 응답시간보다 DB가 데이터를 어떤 경로로 읽는지 확인하는 것을 최적화의 출발점으로 잡았습니다.

02

Problem

문제는 “데이터가 많아서 느리다”가 아니라 어떤 방식으로 읽고 정렬하는지에 있었습니다.

Scan

복합 조건 조회에서 넓은 범위를 탐색하는 실행 계획이 나타날 수 있었습니다.

  • 조회 조건에 맞는 인덱스가 없으면 Full Scan 가능
  • 결과는 적어도 읽어야 하는 Row는 많을 수 있음
  • 데이터 증가에 따라 I/O 비용이 함께 증가
Sort

조회 조건과 정렬 조건이 인덱스 순서와 맞지 않으면 별도 정렬이 필요했습니다.

  • ORDER BY가 인덱스 순서와 맞지 않으면 Filesort 가능
  • 조건 검색 후 다시 정렬하는 추가 비용 발생
  • 대량 데이터에서 정렬 비용이 더 크게 드러남
“인덱스를 만들었다”가 아니라,
EXPLAIN에서 실제 접근 방식과 탐색 범위가 어떻게 바뀌었는지를 기준으로 판단했습니다.
03

Test Data

성능 차이가 실행 계획에 드러나도록 약 10만 건 규모의 테스트 환경을 만들었습니다.

적은 데이터에서는 Full Scan과 Index Range Scan의 차이가 응답시간에 크게 드러나지 않을 수 있습니다. 따라서 조회 대상 데이터가 충분히 많아졌을 때 접근 방식의 차이를 확인할 수 있도록 테스트 데이터를 대량으로 구성했습니다.

비교 시에는 동일한 조건과 정렬 기준을 유지한 채 인덱스 적용 전후 EXPLAIN을 반복해 확인했습니다. 로컬 머신의 순간적인 CPU 상태에 영향을 받는 단일 응답시간보다 type·key·rows·Extra 변화에 집중했습니다.

04

EXPLAIN Analysis

EXPLAIN의 type·key·rows·Extra를 기준으로 Full Scan과 정렬 비용을 추적했습니다.

실제 프로젝트의 테이블·필드 구조는 별도로 유지하고, 아래 실행 계획은 당시 분석 방법을 보여주기 위해 단순화한 재구성 예시입니다. 핵심은 특정 컬럼명이 아니라 복합 조건 검색에서 적절한 인덱스가 없을 때 어떤 실행 계획이 나타나고, 이를 어떻게 해석했는지에 있습니다.

조건 검색과 최신순 정렬이 함께 수행되는 조회를 기준으로 인덱스 적용 전에는 전체 범위를 넓게 읽고 별도 정렬하는 형태, 적용 후에는 조건에 맞는 연속 구간만 읽는 Range Scan 형태를 비교했습니다.

Before · 구조를 단순화한 예시 
SELECT ...
FROM target_table
WHERE condition_a = ?
  AND condition_b = ?
  AND range_column >= ?
ORDER BY sort_column DESC
LIMIT 100;
type possible_keys key rows filtered Extra
ALL NULL 또는 부적합한 단일 인덱스 NULL 약 100,000 약 2~10% Using where; Using filesort

※ 위 수치는 실제 원본 EXPLAIN을 복원한 값이 아니라, 10만 건 환경에서의 분석 흐름을 설명하기 위한 예시입니다.

01

type = ALL

조건에 맞는 인덱스를 선택하지 못하고 대상 테이블의 넓은 범위를 읽는 실행 계획으로 해석했습니다.

02

key = NULL

인덱스가 없거나, 존재하더라도 현재 WHERE·ORDER BY 조합에 적합하지 않아 실제 실행에서 선택되지 않은 상태로 판단했습니다.

03

rows ≈ 100,000

반환 결과가 적더라도 DB가 결과를 찾기 위해 읽는 예상 범위가 크다면 데이터 증가에 따라 비용이 계속 커질 수 있다고 봤습니다.

04

Using filesort

정렬 조건을 인덱스로 해결하지 못하고 별도 정렬 작업이 필요하다는 신호로 보고,
조회 조건과 정렬 순서를 함께 만족시키는 인덱스를 검토했습니다.

05

Index Strategy

자주 함께 사용되는 조건과 정렬 기준을 하나의 복합 인덱스 흐름으로 설계했습니다.

이전 프로젝트에서 배운 것처럼 단일 인덱스를 여러 개 만드는 것보다, 실제 API가 사용하는 WHERE 조건과 ORDER BY의 조합을 하나의 조회 패턴으로 보고 복합 인덱스 컬럼 순서를 결정하는 것이 중요했습니다.

일반적으로 동등 조건으로 좁히는 컬럼을 앞쪽에 두고, 이후 범위 조건과 정렬에 사용되는 컬럼을 이어 배치하는 방향으로 검토했습니다. 적용 후에는 EXPLAIN을 다시 실행해 type이 range 계열로 바뀌는지, 실제 key에 복합 인덱스가 선택되는지, rows와 filesort가 줄었는지를 확인했습니다.

Composite Index · 개념 예시 
CREATE INDEX idx_target_search
ON target_table (
  equality_column_1,
  equality_column_2,
  range_or_sort_column DESC
);
type possible_keys key rows filtered Extra
range idx_target_search idx_target_search 약 20,000~50,000 상향 Using index condition

※ After 수치도 설명용 범위입니다. 실제 포트폴리오에서 강조할 부분은 ALL → range, key 선택, 탐색 Row 감소, filesort 제거 여부와 같은 실행 계획의 변화입니다.

Before
  1. 조회 패턴과 인덱스 설계가 분리됨
  2. type = ALL 가능
  3. 넓은 범위 탐색
  4. Using filesort 발생
→
After
  1. WHERE + ORDER BY 기준 복합 인덱스 설계
  2. type = range 계열로 개선
  3. 필요 구간 중심 탐색
  4. 정렬 추가 작업 감소 또는 제거
Index Order

복합 인덱스의 컬럼 순서는 SQL에 적힌 WHERE 절의 문자 순서를 그대로 따라가는 것이 아니라,
동등 조건·범위 조건·정렬 방식과 실제 데이터 분포를 함께 고려해 결정했습니다.

06

Trade-off

조회 성능을 높이는 인덱스도 쓰기 비용과 저장 공간을 사용하는 자원이었습니다.

Read

조회 패턴에 맞는 인덱스는 탐색 범위와 정렬 비용을 줄일 수 있습니다.

  • 복합 조건 조회 범위 축소
  • ORDER BY 추가 정렬 비용 감소 가능
  • 대량 데이터에서 효과가 더 분명하게 나타남
Write

인덱스가 늘어나면 INSERT·UPDATE 시 유지 비용도 함께 증가합니다.

  • 데이터 변경 시 인덱스 엔트리도 갱신
  • 추가 저장 공간 사용
  • 중복·미사용 인덱스는 오히려 비용 증가
More Indexes 무조건적인 인덱스 추가

특정 조회는 빨라질 수 있지만 실제 쿼리에서 선택되지 않는 인덱스가 늘어나면 쓰기 비용과 관리 복잡도만 증가할 수 있습니다.

What I learned

데이터베이스 최적화는 “느린 쿼리를 감으로 고치는 것”이 아니라 실행 계획으로 원인을 확인하고 다시 검증하는 과정이었습니다.

이전 성능 개선 경험에서 Full Scan, 실시간 집계, N+1과 같은 병목을 실행 계획과 로그로 분리해 봤던 방식이 이번 프로젝트에서도 기준이 됐습니다. 현재 프로젝트에서는 약 10만 건의 데이터를 직접 구성하고, 조회 조건과 정렬 패턴이 인덱스와 어떻게 연결되는지를 중심으로 분석했습니다. 이를 통해 단순히 인덱스를 추가하는 것보다 실제 조회 패턴과 데이터 접근 경로를 함께 설계하는 것이 중요하다는 점을 다시 확인했습니다.

  • 느린 조회는 먼저 데이터 규모와 EXPLAIN 결과로 병목을 분리
  • type·key·rows·Extra를 함께 보면서 Full Scan과 정렬 비용을 해석
  • WHERE 조건과 ORDER BY를 하나의 조회 패턴으로 보고 복합 인덱스를 설계
  • 인덱스 적용 후 동일 쿼리의 실행 계획을 다시 확인해 실제 선택 여부를 검증
  • 읽기 성능뿐 아니라 INSERT·UPDATE 비용과 저장 공간까지 함께 고려
