Spring Security 환경의 CORS 요청 실패
원인 분석 및 해결

로컬 프론트엔드에서 JWT 인증 API를 호출하는 과정에서 CORS 오류가 발생했습니다. 브라우저의 Same-Origin Policy와 Preflight 요청 흐름을 확인하고, WebMvcConfigurer와 SecurityFilterChain의 처리 위치 차이를 분석해 CORS 설정을 Spring Security 레벨로 통일했습니다.

카테고리 : Backend / Security / Troubleshooting · 2025.11 ~ 2026.01
Java Spring Boot Spring Security JWT
01

Overview

서버는 정상인데 브라우저에서만 API 요청이 실패했습니다.

로컬 개발 환경에서 프론트엔드는 http://localhost:3000, 백엔드는 http://localhost:8080으로 실행하고 있었습니다. 호스트 이름은 같지만 포트가 달라 브라우저 기준으로는 서로 다른 Origin이었고, 프론트엔드에서 API를 호출하는 순간 CORS 오류가 발생했습니다.

Postman과 서버 자체 테스트에서는 API가 정상적으로 동작해 처음에는 백엔드 API 문제인지 판단하기 어려웠습니다. 하지만 브라우저 요청 흐름을 확인하면서 CORS는 서버 자체의 기능 오류라기보다 브라우저의 Same-Origin Policy와 서버의 허용 정책이 맞지 않을 때 발생한다는 점을 문제의 출발점으로 잡았습니다.

3000 로컬 프론트엔드 개발 서버 포트
8080 로컬 Spring Boot API 서버 포트
OPTIONS 실제 요청 전에 발생한 Preflight 메서드
Security 최종적으로 CORS 처리를 통일한 계층
02

CORS

브라우저는 Scheme·Host·Port가 모두 같아야 같은 Origin으로 판단합니다.

CORS는 Cross-Origin Resource Sharing의 약자로, 브라우저의 Same-Origin Policy가 차단하는 교차 출처 요청을 서버의 허용 정책에 따라 예외적으로 허용하는 방식입니다.

Origin은 Scheme, Host, Port의 조합으로 결정됩니다. 따라서 localhost라는 호스트가 같더라도 3000과 8080처럼 포트가 다르면 브라우저에서는 다른 출처로 판단합니다.

Frontend

http://localhost:3000

  • React 또는 Next.js 개발 서버
  • 브라우저가 요청을 시작하는 Origin
  • 백엔드 8080 포트와 다른 출처
Backend

http://localhost:8080

  • Spring Boot API 서버
  • CORS 허용 정책을 응답에 포함해야 함
  • 브라우저 요청 Origin과 포트가 다름
서버가 응답할 수 있다는 사실과 브라우저가 그 응답을 프론트엔드 코드에 전달해 준다는 사실은 별개의 문제였습니다.
03

Preflight

실제 요청보다 먼저 들어온 OPTIONS 요청이 Security에서 막히고 있었습니다.

JWT를 Authorization 헤더로 전달하거나 PUT·PATCH·DELETE와 같은 메서드를 사용하면 브라우저는 실제 요청 전에 OPTIONS 요청으로 서버의 허용 여부를 확인할 수 있습니다. 이 사전 확인 요청이 Preflight입니다.

문제는 이 OPTIONS 요청이 일반 인증 요청처럼 처리되면서 Security Filter Chain에서 401 또는 403으로 종료될 수 있다는 점이었습니다. Preflight가 실패하면 브라우저는 뒤의 실제 POST·PUT·DELETE 요청 자체를 보내지 않기 때문에 프론트엔드에서는 CORS 오류만 보이게 됩니다.

Failure Flow
  1. 브라우저에서 JWT API 호출 시도
  2. OPTIONS Preflight 전송
  3. Security 인증/인가 규칙 적용
  4. 401 / 403 응답
  5. 브라우저가 실제 요청 차단
→
Expected Flow
  1. OPTIONS Preflight 전송
  2. 허용 Origin·Method·Header 확인
  3. CORS 응답 헤더 반환
  4. 브라우저가 본 요청 허용
  5. JWT 인증 필터에서 실제 요청 처리
Why Browser Only?

Postman은 브라우저의 Same-Origin Policy와 같은 흐름을 그대로 적용하지 않기 때문에 API 자체는 정상인데 브라우저에서만 실패하는 상황이 만들어질 수 있었습니다. 이 차이를 확인하면서 서버 기능 오류와 CORS 오류를 분리할 수 있었습니다.

04

Root Cause

MVC에 CORS를 설정해도 Security가 더 앞에서 요청을 종료하면 적용될 기회가 없었습니다.

초기에는 WebMvcConfigurer를 이용해 전역 CORS 설정을 추가했습니다. 허용 Origin과 HTTP Method, Header를 지정했지만, Spring Security가 적용된 프로젝트에서는 이것만으로 문제가 해결되지 않았습니다.

요청이 MVC 레이어에 도달하기 전에 Security Filter Chain에서 종료되면 MVC 레벨의 CORS 처리까지 진행되지 않을 수 있습니다. 특히 OPTIONS 요청이 인증되지 않은 요청으로 판단돼 먼저 차단되면 브라우저가 기대하는 CORS 응답 헤더가 내려갈 기회 자체가 사라지는 구조였습니다.

MVC Only WebMvcConfigurer

MVC 레이어에서 CORS 정책을 정의할 수 있지만, Security Filter Chain에서 요청이 먼저 종료되는 흐름까지 일관되게 제어하기 어려웠습니다.

→
Selected SecurityFilterChain

CORS 처리를 Security 레벨로 올리고 Preflight부터 실제 인증 요청까지 하나의 처리 흐름으로 통일했습니다.

05

Security CORS

SecurityFilterChain에서 CORS를 활성화하고 Preflight 요청을 명시적으로 허용했습니다.

최종적으로 CORS의 처리 위치를 Spring Security로 통일했습니다. SecurityFilterChain에서 CorsConfigurationSource를 사용하도록 설정하고, OPTIONS 요청은 인증 전에 통과할 수 있도록 허용했습니다.

SecurityFilterChain 
http
    .cors(cors ->
        cors.configurationSource(corsConfigurationSource())
    )
    .authorizeHttpRequests(auth -> auth
        .requestMatchers(HttpMethod.OPTIONS, "/**").permitAll()
        // ...
    )
    .sessionManagement(session ->
        session.sessionCreationPolicy(SessionCreationPolicy.STATELESS)
    );

http.addFilterBefore(
    jwtAuthenticationFilter,
    UsernamePasswordAuthenticationFilter.class
);
01

Security에서 CORS 활성화

CorsConfigurationSource를 Security Filter Chain에 연결해 Preflight 요청도 Security 흐름 안에서 일관되게 CORS 정책을 적용받도록 했습니다.

02

OPTIONS 요청 허용

브라우저의 사전 검사 요청이 JWT 인증 이전 단계에서 막히지 않도록 OPTIONS 요청을 명시적으로 permitAll 처리했습니다.

03

Stateless JWT 구조 유지

실제 API 요청의 인증은 기존 JWT 필터에서 처리하되, Preflight와 인증 요청의 역할을 분리하여 Stateless 인증 구조를 유지했습니다.

06

Origin Policy

개발·배포 환경의 Origin을 명시적으로 관리하고 Credentials 정책과 맞췄습니다.

CORS를 단순히 모든 Origin에 열어두는 방식보다는 실제 프론트엔드가 사용하는 Origin을 명시적으로 허용했습니다. 로컬 개발 환경과 배포 도메인을 함께 관리하면서 Method와 Header 정책도 프론트 요청과 일치하도록 구성했습니다.

특히 credentials를 허용하는 설정을 사용할 때는 허용 Origin을 구체적으로 관리해야 하므로, 와일드카드 하나로 모든 환경을 처리하지 않고 허용 목록을 분명히 두었습니다.

CorsConfigurationSource · Example 
CorsConfiguration config = new CorsConfiguration();

config.setAllowedOrigins(List.of(
    "http://localhost:3000",
    "https://wego.monster",
    "https://api.wego.monster",
    "https://local.wego.monster",
    "https://local.wego.monster:3000"
));

config.setAllowedMethods(List.of(
    "GET", "POST", "PUT", "PATCH", "DELETE", "OPTIONS"
));

config.setAllowedHeaders(List.of("*"));
config.setAllowCredentials(true);
Single Owner

WebMvcConfigurer와 SecurityFilterChain 양쪽에서 CORS를 중복 관리하지 않고, Security가 최종 CORS 정책을 책임지도록 설정 위치를 하나로 통일했습니다. 설정이 어디에서 적용되는지 명확해져 환경별 디버깅도 쉬워졌습니다.

07

Result

CORS 오류를 설정 문제로만 보지 않고 브라우저와 Security의 요청 흐름으로 추적했습니다.

Browser Origin 차이 확인

localhost 환경에서도 포트가 다르면 다른 Origin이라는 점을 기준으로 브라우저 차단 원인을 분리했습니다.

Preflight OPTIONS 흐름 정상화

Preflight가 인증 필터에서 먼저 실패하지 않도록 CORS 처리와 OPTIONS 허용 규칙을 Security에 반영했습니다.

Configuration CORS 설정 단일화

MVC와 Security에 분산되어 있던 CORS 책임을 SecurityFilterChain 중심으로 정리했습니다.

What I learned

CORS 오류를 해결하려면 헤더 하나보다 브라우저가 어떤 순서로 요청을 보내는지 이해해야 했습니다.

처음에는 서버 설정 하나만 추가하면 끝나는 문제라고 생각했지만, 실제 원인은 브라우저의 Origin 판단, Preflight 요청, Spring Security Filter Chain과 MVC의 처리 순서가 함께 얽혀 있었습니다. 특히 Postman에서는 정상인데 브라우저에서만 실패하는 현상을 통해 애플리케이션 기능 문제와 브라우저 보안 정책 문제를 분리해서 보는 관점을 배웠습니다.

  • CORS는 Scheme·Host·Port로 구분되는 Origin 정책에서 시작
  • Authorization 헤더 등으로 Preflight가 발생할 수 있으므로 OPTIONS 흐름을 함께 확인
  • Spring Security가 요청을 먼저 처리하는 구조에서는 CORS도 Security 레벨에서 함께 설계
  • Preflight와 실제 JWT 인증 요청의 역할을 분리해 Stateless 인증 구조 유지
  • CORS 설정 위치를 하나로 통일해 중복 설정과 환경별 차이를 줄임
